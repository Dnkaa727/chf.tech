# Патч: мягкая привязка цитат и исправление Stage 2 schema_mismatch

## Что меняется

### 1. `invalid_quote` больше не обрывает двухэтапную оценку

Stage 1 по-прежнему выполняет LLM: она сама выделяет смысловые сегменты и связывает их с критериями. Python не разбивает ответ на предложения и не пытается самостоятельно выделять смысловые части.

После получения сегментов Python пытается привязать формулировку `quote` к исходному ответу:

- `matched` — найдено точное или нормализованное совпадение. В сегмент записывается исходный фрагмент и позиции `start` / `end`.
- `unverified` — непустую формулировку найти не удалось. Сегмент сохраняется с исходной формулировкой LLM, `start = null`, `end = null`. Оценка продолжается.
- Если Stage 1 повторно возвращает уже найденную цитату, Python сначала использует ещё не занятое вхождение, а при исчерпании вхождений повторно использует найденный диапазон. Повторная запись одного и того же фрагмента сама по себе не превращает его в `unverified`.

Пустая цитата по-прежнему считается некорректной структурой Stage 1 и не принимается.

`unverified` не означает автоматически, что LLM придумала содержание. Это означает только, что автоматическая привязка к исходному тексту не состоялась. Проверка смыслового соответствия остаётся человеку.

### 2. Как узнать, что нужна ручная проверка

Результат содержит:

- `source_alignment_review_required` — `true`, если есть хотя бы один `unverified` сегмент;
- `unverified_segment_ids` — список таких ID;
- `segment_alignment` — полный список сегментов с `segment_id`, `text`, `source_alignment`, `start`, `end`, `claim_type` и `criterion_links`.

В доказательствах критериев и Red Flags также указывается `source_alignment` и, когда доступны, `start` / `end`.

При наличии `unverified` результат получает `needs_review = true`. Публичный результат оценки скрывает итоговый балл (`score = null`) до ручной проверки. Само наличие `unverified` не добавляется в общий `warnings`: в текущей сессионной логике непустой `warnings` трактуется как ошибка оценки и может завершить запрос с 502. Для ручной проверки используются отдельные поля выше.

### 3. Исправление `schema_mismatch` в Stage 2

Раньше `segment_assessments` передавался как массив объектов. При этом JSON Schema для критерия без связанных сегментов допускала глобальные ID, а Python-валидатор ожидал только ID, связанные с конкретным критерием. Контракт схемы и локальная проверка расходились.

Теперь Stage 2 возвращает `segment_assessments` как объект, где ключ — ID сегмента, значение — его отношение к критерию.

Для критерия с двумя сегментами:

```json
{
  "segment_assessments": {
    "S001": "supports",
    "S002": "neutral"
  }
}
```

Для критерия без связанных сегментов используется специальный маркер:

```json
{
  "segment_assessments": {
    "__no_evidence__": "not_applicable"
  }
}
```

Динамическая JSON Schema требует все связанные ID, запрещает дополнительные ключи и исключает дублирование одного сегмента. Для критерия без сегментов схема требует только маркер `__no_evidence__`.

**Важно:** live-провайдер Stage 2 должен возвращать новый объектный формат, а не старый массив. В локальном Python-пути оставлена совместимость со старыми массивами для существующих внутренних тестов/вызовов; JSON Schema провайдера использует новый формат.

### 4. Работа с error updates / resolutions

В двухэтапном режиме после проверки связей по `segment_id` не требуется повторно доказывать дословное совпадение каждой формулировки. Поэтому `unverified` сегменты могут участвовать в evidence/error-update/resolution структуре и будут явно помечены статусом привязки.

Одноэтапный режим сохраняет прежнюю строгую проверку дословных цитат.

### 5. Диагностика Stage 2

Локальные ошибки проверки ответа теперь сохраняют `stage` в диагностике, чтобы `schema_mismatch` было проще отличить от ошибки сегментации и от сбоя провайдера.

## Установка в Windows PowerShell

Остановите запущенный Uvicorn (`Ctrl+C`). Перейдите в корень проекта:

```powershell
cd D:\RAG_BACKEND_ALL_25
```

Распакуйте архив во временную папку:

```powershell
Expand-Archive .\RAG_BACKEND_ALL_25_SOFT_QUOTE_SCHEMA_PATCH.zip .\_soft_quote_schema_patch -Force
```

Сделайте резервные копии файлов, которые будут заменены:

```powershell
$stamp = Get-Date -Format 'yyyyMMdd_HHmmss'
New-Item -ItemType Directory -Force ".\_backup_soft_quote_$stamp" | Out-Null
Copy-Item .\v3\engine.py ".\_backup_soft_quote_$stamp\engine.py"
Copy-Item .\v3\llm.py ".\_backup_soft_quote_$stamp\llm.py"
```

Скопируйте новые файлы:

```powershell
Copy-Item .\_soft_quote_schema_patch\v3\engine.py .\v3\engine.py -Force
Copy-Item .\_soft_quote_schema_patch\v3\llm.py .\v3\llm.py -Force
```

Тесты из архива скопируйте в папку `tests` проекта (необязательно для запуска приложения, но рекомендуется):

```powershell
Copy-Item .\_soft_quote_schema_patch\tests\*.py .\tests\ -Force
```

Проверьте синтаксис и тесты:

```powershell
.\.venv\Scripts\python.exe -m py_compile .\v3\engine.py .\v3\llm.py
.\.venv\Scripts\python.exe -m pytest .\tests\test_v3_soft_quote_schema.py .\tests\test_v3_two_stage.py .\tests\test_v3_red_flag_checklist.py .\tests\test_v3_root_cause_schema.py -q
```

Запустите сервер обычной командой проекта:

```powershell
.\.venv\Scripts\python.exe -m uvicorn app.api:app --host 127.0.0.1 --port 8000
```
