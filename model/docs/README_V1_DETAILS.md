# Python Backend RAG MVP — передача ML-инженеру

**Статус:** рабочее локальное демо, **не production**. Данные основаны на 8 отобранных вакансиях Python Backend. 25 карточек на 20 компетенций. **Все вопросы и критерии — черновики**, требуется проверка техническим экспертом.

## 1. Что работает

- Legacy: 25 структурированных карточек в `data/legacy/knowledge_base_v1.json`:
  компетенция, тема, вопрос, 3 исторических критерия, уточнение, происхождение.
  Новый каталог и оценивание описаны в [REGISTRY_V3_RU.md](REGISTRY_V3_RU.md).
- Объяснимый **лексический поиск** по компетенции, синонимам, тегам и теме (без embeddings и без векторной БД).
- Подготовка RAG-контекста как массива `[{"role":"system", "content":"..."},{"role":"user", ...}]` для ML-инженера.
- Готовый вопрос в режиме `template` **без LLM**.
- Режим `llm`: HTTP вызов OpenAI-совместимого `/chat/completions`, возврат вопроса.
- Режим оценки `evaluate`: LLM предлагает подтверждённые критерии; сервер проверяет **дословное вхождение цитат** в ответ кандидата. Итоговые баллы не рассчитываются.
- HTTP API (FastAPI), Swagger по `/docs`, CLI и unit-тесты.

**Пока нет:** STT/TTS, реального многоходового управления интервью и памяти сессий, аутентификации пользователей, шифрования и согласования обработки ПДн, полноценной экспертной валидации, semantic embeddings и автоматического HR-решения.

## 2. Быстрый запуск на Windows PowerShell

Нужен Python **3.10+** (лучше 3.11 или 3.12), доступный как `py`.

1. Распакуй архив. Открой PowerShell **в папке `python_backend_rag_mvp`** (где лежит `cli.py`).
2. Поиск и заготовки вопросов работают даже без установки зависимостей:

```powershell
py cli.py list
py cli.py search "индексы PostgreSQL"
py cli.py search "asyncio" --competency Python
py cli.py question --card-id PG-QUERY-01
py cli.py question --card-id PG-QUERY-01 --answer "Индексы всегда ускоряют запросы"
py cli.py prepare --card-id PG-QUERY-01 --answer "Индексы всегда ускоряют запросы"
py -m unittest discover -s tests -v
```

3. Для запуска REST API:

```powershell
py -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m uvicorn app.api:app --host 127.0.0.1 --port 8000
```

Открой **http://127.0.0.1:8000/docs**. Здесь можно вызывать эндпоинты без PowerShell.

### Проверка API без нейросети

В Swagger используй `POST /v1/retrieve` с телом:

```json
{"query":"индексы PostgreSQL","limit":3}
```

Для `POST /v1/question`:

```json
{"card_id":"PG-QUERY-01","mode":"template"}
```

Или в PowerShell (второе окно):

```powershell
$body = '{"query":"индексы PostgreSQL","limit":3}'
Invoke-RestMethod -Uri 'http://127.0.0.1:8000/v1/retrieve' -Method POST -ContentType 'application/json; charset=utf-8' -Body ([Text.Encoding]::UTF8.GetBytes($body)) | ConvertTo-Json -Depth 6
```

## 3. Подключение реальной LLM через API

Наш адаптер подходит для провайдера, у которого есть **OpenAI-compatible Chat Completions API**. У некоторых российских провайдеров другой HTTP протокол и авторизация — тогда ML-инженеру потребуется отдельный адаптер. Наличие API само по себе **не гарантирует совместимость**.

В новой PowerShell-сессии **до запуска сервера** настрой переменные (ключ ниже — лишь пример-заглушка):

```powershell
$env:LLM_BASE_URL = "https://api.openai.com/v1"
$env:LLM_MODEL = "УКАЖИ_ДОСТУПНУЮ_ТЕБЕ_МОДЕЛЬ"
$env:LLM_API_KEY = "ВСТАВЬ_ЛИЧНЫЙ_API_КЛЮЧ"
$env:LLM_TIMEOUT_SECONDS = "40"

.\.venv\Scripts\python.exe -m uvicorn app.api:app --host 127.0.0.1 --port 8000
```

**Не вставляй реальный ключ в Python/JSON, GitHub, скриншоты и сообщения кандидатов.** Значение `$env:` действует в текущей сессии PowerShell; `\.env.example` — образец, автоматически не читается.

После этого в Swagger используй `POST /v1/question`:

```json
{"card_id":"PG-QUERY-01","candidate_answer":"Индексы всегда ускоряют запросы","mode":"llm"}
```

Ожидаемый формат (пример, не реальный ответ модели):

```json
{"card_id":"PG-QUERY-01","question":"В каких ситуациях PostgreSQL выберет seq scan?","mode":"llm","review_status":"draft_needs_expert_review"}
```

Далее `POST /v1/evaluate` (только с API и только для внутреннего интерфейса):

```json
{"card_id":"PG-QUERY-01","candidate_answer":"Индексы всегда ускоряют запросы"}
```

Ответ возвращает `confirmed` с **дословными** цитатами, `unconfirmed`, `followup`, `score: null`, `human_review_required: true`. **Нет** оснований считать автоматически предложенную оценку объективной: проверка цитаты на вхождение — не экспертная валидация смысла.

### Переключение на self-hosted Qwen

Если ML-инженер позже поднимет Qwen в OpenAI-совместимом сервере (например, vLLM), RAG менять не нужно. Поменяйте только переменные:

```powershell
$env:LLM_BASE_URL = "http://127.0.0.1:8001/v1"
$env:LLM_MODEL = "ИМЯ_МОДЕЛИ_НА_ВАШЕМ_СЕРВЕРЕ"
$env:LLM_API_KEY = "КЛЮЧ_ЛОКАЛЬНОГО_СЕРВЕРА"
```

Этот переход **потребует сравнения качества** ответов; сам по себе общий API не гарантирует одинаковую структуру JSON или качество генерации.

## 4. Контракт API для команды

| Метод | URL | Назначение |
|---|---|---|
| `GET` | `/health` | Проверка сервиса и числа карточек |
| `GET` | `/v1/competencies` | Список ID / тем без скрытых критериев |
| `POST` | `/v1/retrieve` | Найти релевантные карточки |
| `POST` | `/v1/prepare` | Готовые сообщения `system` + `user`, включая черновую рубрику — **только ML/backend** |
| `POST` | `/v1/question` | Вопрос: `mode=template` или `mode=llm` |
| `POST` | `/v1/evaluate` | Анализ ответа через LLM и дословные цитаты |

### Пример `POST /v1/prepare`

```json
{"card_id":"PG-QUERY-01","candidate_answer":"Индексы всегда ускоряют запросы","task":"question"}
```

Он возвращает `messages`, которые можно напрямую передать в клиент LLM как `messages=...`. Это особенно удобно ML-инженеру: он может **полностью заменить `app/llm.py`**, не трогая retrieval и карточки.

### Какая часть за кем

- **Аналитик:** JSON карточки, качество требований вакансий, разметка приоритетов, точность retrieval, сбор эталонных оценок вместе с экспертом.
- **ML:** клиент выбранной LLM, управление диалогом, стабильный JSON-output, latency, STT/TTS, тестирование моделей.
- **Backend:** сессии, права доступа, хранение согласий и данных, логи с маскировкой, rate limiting, интеграция интерфейса.

### Структура одной карточки

- `competency` и `topic` — **что** интервьюировать.
- `question` — предложенный основной вопрос.
- `criteria` — наблюдаемые признаки правильного ответа (пока черновые).
- `followup_questions` — заготовки уточняющих вопросов.
- `source_vacancies` — подтверждение, что **тема востребована**, а не источник технически правильного ответа.
- `review_status` — во всех карточках `draft_needs_expert_review`.
- `priority_for_demo` — **наше проектное решение** `core/extended/optional`, а не обязательность каждой компетенции в каждой вакансии.
- `mention_count_in_8_vacancies` — число вакансий из ограниченной выборки, не доля всего рынка.

## 6. Критические ограничения

1. **Сервис без авторизации.** Запускай только на `127.0.0.1`. Нельзя публиковать прямо в интернет или делать эндпоинты с рубриками доступными кандидату.
2. **Персональные данные:** тестируй на вымышленных кандидатах. Перед передачей реальных голосовых записей/транскрипций внешнему провайдеру — согласие, договор/условия обработки, ИБ и юрист банка.
3. **Рубрики не проверены:** вопросы и критерии предложены для демо; соответствие вакансии не гарантирует их корректность.
4. **Поиск лексический:** embeddings нет. Непохожие формулировки иногда не найдутся. Отлаживать по полю `matches` / `score`.
5. **Нет сессий/истории:** бэкенду нужно передавать актуальный `candidate_answer` и выбирать `card_id`. Многоходовое интервью и отчёт требуют отдельного оркестратора.
6. **LLM не даёт достоверную оценку автоматически:** приложение требует буквальную цитату, но не проверяет её соответствие техническому критерию. Баллы и решение о найме оставлены человеку.
7. JSON ответ LLM может оказаться неправильным. `llm.py` возвращает ошибку — это лучше, чем незаметно подменить результат выдуманной оценкой. В production нужны ретраи, контроль схемы и метрики.
8. Для локального self-hosted LLM нужно подтвердить поддерживаемый chat template и Chat Completions API. vLLM документация: https://docs.vllm.ai/en/latest/serving/online_serving/openai_compatible_server/
