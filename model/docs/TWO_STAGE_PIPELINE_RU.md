# Двухэтапная оценка ответа по рубрике

В v3 по умолчанию включён конвейер `two_stage`. Он использует два обращения к LLM.

## Поток данных

1. **Смысловое разбиение и маршрутизация.** Первый вызов выделяет атомарные технические утверждения из ответа и связывает каждый фрагмент с одним или несколькими `criterion_id`. На этом этапе связь означает тематическую релевантность, а не правильность утверждения.
2. **Проверка фрагментов в Python.** Python находит каждый `quote` в исходном ответе, заменяет его точным исходным фрагментом, назначает ID `S001`, `S002` и проверяет, что все ссылки ведут к существующим критериям. Если цитату нельзя надёжно сопоставить, оценка прекращается с ошибкой валидации.
3. **Оценка по рубрике.** Второй вызов получает исходный ответ, все проверенные фрагменты, полную рубрику и состояние предыдущих ошибок. Он по-прежнему оценивает все пять критериев за один запрос и выставляет 0/1/2. Для каждого критерия модель возвращает объект `segment_assessments`: ключ — `segment_id`, значение — ровно одна категория: `supports`, `partially_supports`, `contradicts` или `neutral`.
4. **Проверка и сбор результата в Python.** JSON Schema для каждого критерия заранее содержит все и только связанные с ним ID как обязательные ключи; посторонние ключи запрещены. Поэтому один сегмент нельзя одновременно поместить в две категории, а обязательный сегмент нельзя пропустить. Python проверяет также полный список просмотренных сегментов, затем сам преобразует `segment_assessments` в внутренние записи `evidence`. Цитаты для результата берутся только из исходного ответа.

## Переключение режима

В `.env` или в переменных окружения процесса сервера: 

```dotenv
LLM_PIPELINE_MODE=two_stage
LLM_MESSAGE_MODE=system_user
LLM_JSON_MODE=schema
```

`two_stage` — основной режим. `one_stage` оставлен для baseline-сравнения со старым оценщиком:

```dotenv
LLM_PIPELINE_MODE=one_stage
```

Оба режима используют те же рубрики и API `/v3/evaluate`. После изменения переменных окружения перезапустите Uvicorn. Не помещайте API-ключ в архив проекта.

## Формат доказательств

В ответе `/v3/evaluate` у каждого критерия сохраняются прежние поля `points`, `quote`, `reason` и добавляется `evidence` — список фрагментов с `segment_id`, точной цитатой и отношением к критерию. Внутренний формат Stage 2 изменён: вместо четырёх массивов используется `segment_assessments`, а Python строит `evidence`. `quote` остаётся одной основной цитатой для совместимости. Внешний контракт API не меняется. В сессионном состоянии набор сегментов также сохраняется в истории доказательств.

## Проверки

```powershell
python -m unittest discover -s tests -p "test_v3_two_stage.py"
python -m unittest discover -s tests -p "test_*.py"
```

Unit-тесты проверяют структуру и валидацию конвейера, но не доказывают качество ответов реальной модели. Для оценки качества используйте одинаковые ответы, рубрики и модель в режимах `one_stage` и `two_stage`; экспертные эталонные оценки нужны для расчёта точности. Двухэтапный режим делает два вызова LLM на ответ, поэтому обычно увеличивает стоимость и задержку.

## Ограничения

- Проверка в Python гарантирует точность цитат и ссылок, но не гарантирует, что первая модель выделила абсолютно каждое важное утверждение. Полноту сегментации нужно отдельно измерять на экспертно размеченных ответах.
- Фиксированные ключи в `segment_assessments` гарантируют полноту и однозначность структуры, но не гарантируют правильность самой смысловой классификации. Модель всё ещё может ошибочно назвать подтверждающий фрагмент противоречащим; это нужно проверять на экспертно размеченных ответах.
- Если Stage 1 вообще не выделил важный фрагмент, Python не может восстановить неизвестный смысл автоматически. Поэтому нужны тесты на короткие, длинные, противоречивые и разговорные ответы.
- Рубрики в каталоге остаются черновыми и требуют экспертной валидации. Результат не должен автоматически использоваться как решение о найме.
