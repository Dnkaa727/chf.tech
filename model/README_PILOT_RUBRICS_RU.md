# Пилот переработки рубрик: 3 карточки

Пилот меняет только формулировки уже существующих полей в трёх карточках:

- `PY-ASYNC-01` — асинхронность Python;
- `PG-TX-01` — транзакции и конкурентное списание в PostgreSQL;
- `API-VAL-01` — валидация и обработка ошибок в FastAPI.

## Что меняется

- формулировка вопроса в `rubrics_all_25.json` и соответствующей карточке в `knowledge_base.json`;
- названия пяти критериев и якоря `0`, `1`, `2`;
- `followup_question` для каждого критерия;
- версия затронутых рубрик становится `3.1-pilot`, а в `review_note` добавляется отметка о пилоте.

**Что не меняется:** JSON-схемы, количество карточек, количество критериев (5 на карточку), шкала 0–2, код API и логика evaluator. Нового поля `details` нет. Конкретные библиотеки, SQL-команды и классы не обязательны, когда кандидат объясняет технически корректный эквивалентный механизм.

## Установка в Windows PowerShell

1. Распакуй содержимое архива в корень проекта `D:\RAG_BACKEND_ALL_25`, сохранив папку `tests`.
2. Перейди в корень проекта:

   ```powershell
   cd D:\RAG_BACKEND_ALL_25
   ```

3. Запусти скрипт:

   ```powershell
   .\.venv\Scripts\python.exe .\apply_pilot_rubrics.py
   ```

Скрипт проверяет версии схем, наличие каждой из трёх карточек и совпадение ID пяти критериев. Перед изменением каждого файла создаёт резервную копию вида `*.before_pilot_YYYYMMDD_HHMMSS.bak`. Запускай его из корневой папки проекта. Если проверка структуры не пройдёт, скрипт остановится до изменения JSON.

Архив содержит **патч**, а не полные копии JSON проекта: так сохраняются другие изменения, которые могли быть сделаны в твоей рабочей версии.

## Проверка качества самой LLM

1. Открой `http://127.0.0.1:8000/docs`.
2. Найди `POST /v3/evaluate`.
3. Для каждой карточки отправь три запроса из `PILOT_LIVE_TEST_CASES.json`, используя `card_id` и `candidate_answer`.
4. Сверь баллы по каждому критерию, а не только общий итог:
   - `*_SEMANTIC_STRONG` — целевой профиль `2,2,2,2,2`;
   - `*_PARTIAL` — целевой профиль `1,1,1,1,1`;
   - `*_KEYWORDS_ONLY` — целевой профиль `0,0,0,0,0`;
   - `*_CONFIDENTLY_WRONG` — целевой профиль `0,0,0,0,0`.

Ожидания в JSON — **контрольные ориентиры для экспертного сравнения**, а не гарантия ответа модели. Особенно внимательно проверь частичные ответы: иногда отдельный критерий может обоснованно получить 0 или 2, если реальная цитата сильнее или слабее задуманного уровня. Проверяй обоснования и точные цитаты, а не только число.

При `needs_review=true`, `abstained=true` или `score=null` не пытайся трактовать общий балл как обычный результат: смотри причину перевода на ручную проверку и оценки отдельных критериев.

## Что фиксировать по результатам

Для каждого запроса сохрани:

- `card_id` и `id` тестового случая;
- баллы по пяти критериям;
- `reason` и `evidence` каждого критерия;
- `needs_review`, `abstained`, `uncertainty`;
- расхождения с целевым профилем и экспертное решение.

Критерий успеха пилота — модель засчитывает сильный ответ без обязательных названий API, не начисляет баллы за список терминов, распознаёт ложные утверждения и различает частичное понимание от полного.
