# RAG AI-интервьюер Python Backend — единая версия для 25 карточек

## Что это

Это **локальный технический прототип**, собранный на основе вашей предыдущей RAG-базы и добавленных рубрик.

- **25 карточек** технических вопросов из `data/knowledge_base.json`.
- **Общий валидируемый реестр и выбор карточки:** [REGISTRY_V3_RU.md](docs/REGISTRY_V3_RU.md).
  Каталог больше не содержит критериев; старый формат сохранён отдельно для legacy.
- **25 рубрик** из `data/rubrics_all_25.json`: **5 отдельных критериев** по 0/1/2 балла, 10 баллов максимум на тему.
- **125 привязанных к критериям уточняющих вопросов** (по одному на критерий).
- **150 основных синтетических примеров** из `data/eval_cases_all_25.json` (по шесть на каждую карточку: плохой, средний, отличный, частичный, уверенно неверный, уклончивый).
- **50 дополнительных red-team-кейсов** в `data/redteam_cases_all_25.json`: по одному на prompt injection и off-topic для каждой из 25 тем.
- Оценщик v3 по умолчанию работает в два этапа: смысловое разбиение ответа и маршрутизация фрагментов по критериям, затем оценка по рубрике с проверкой ID доказательств и восстановлением точных цитат. Старый одновызовный режим сохранён для baseline-сравнения.
- FastAPI с REST-эндпоинтами `/v3/*` для **всех 25**. Старые `/v1/*` и `/v2/*` сохранены для совместимости, но `/v2/*` — **устаревшая версия только с PostgreSQL**. Для новых тестов используйте **ТОЛЬКО `/v3/*`**.

**Честное ограничение:** эти рубрики и 150 синтетических ответов подготовлены как *тестовый черновик*. Они **не проверены независимо техническим экспертом**, не являются обучающим корпусом подтверждённого качества и не могут использоваться для автоматических отказов в найме. Прогон реального GPT-4o-mini не выполнялся. Прошедшие offline-тесты подтверждают корректность кода/контрактов, **не точность модели**.

## 1. Запуск на Windows (без API, бесплатно)

1. Распаковать архив, войти в папку `RAG_BACKEND_ALL_25`.
2. Дважды нажать `01_TEST_OFFLINE.bat`.
3. Ожидаемый результат актуального набора: `156 tests ... OK (skipped=4)`; четыре теста пропускаются, пока отдельные рубричные патчи RAG_LOGIC24/PG01 не установлены. Если Windows не видит `py`, проверьте `py --version`.

То же из PowerShell:

```powershell
py run.py check
py run.py test
py run.py cards
py run.py mock PY-ASYNC-01 partial
py run.py mock-all
```

`mock` и `mock-all` **не обращаются к нейросети**. Они подставляют ручные тестовые баллы, чтобы проверить логику: 150/150 synthetic fixtures — это **не accuracy модели**.

## 3. Пример реального оценивания GPT-4o-mini (после замены раскрытых ключей)

**Сначала обязательно отзовите/замените ключи, ранее показанные в переписке. Никому не отправляйте новые ключи.**

Пример настройки при **прямом API OpenAI** (если у ML-инженера другой gateway, запросите у него фактические BASE_URL/MODEL и поддержку JSON Schema, но не присылайте ключ):

```powershell
$env:LLM_BASE_URL = 'https://api.openai.com/v1'
$env:LLM_MODEL = 'gpt-4o-mini'
$env:LLM_PIPELINE_MODE = 'two_stage'
$env:LLM_MESSAGE_MODE = 'system_user'
$secureKey = Read-Host 'Новый API key' -AsSecureString
$env:LLM_API_KEY = [System.Net.NetworkCredential]::new('', $secureKey).Password
py run.py live-one PG-QUERY-01 confident_wrong
```

Для конкретной темы, например Python asyncio:

```powershell
py run.py live-one PY-ASYNC-01 excellent
py run.py live-six PY-ASYNC-01
py run.py live-redteam PY-ASYNC-01
```

`live-one` = **2 платных provider-вызова**, `live-six` = **12**, `live-redteam` = **4** в режиме `two_stage` (по два на каждый ответ). В режиме `one_stage` число вызовов вдвое меньше. Чтобы протестировать **все 150** через настоящую модель:

```powershell
py run.py live-all --confirm-cost
```

**300 платных вызовов в режиме `two_stage` (150 × 2):** запускайте только согласовав расход с ML-инженером. Команда без флага `--confirm-cost` блокируется.

Результаты тестов **без текстов ответов кандидатов** сохраняются в `live_eval_v3_results.json`. После окончания терминала можно очистить ключ:

```powershell
Remove-Item Env:LLM_API_KEY
```

Если gateway поддерживает только JSON mode, можно *явно* выставить `$env:LLM_JSON_MODE='object'`; тогда JSON-формат проверяется на стороне Python, но нет обещания строгого соответствия схеме. Для gateway, принимающего только `system`/`user`, используйте `$env:LLM_MESSAGE_MODE='system_user'`; это рекомендуемое значение в текущем шаблоне.

## 4. HTTP API / Swagger для ML/backend

```powershell
py -m pip install -r requirements.txt
py run.py serve
```

Откройте локально `http://127.0.0.1:8000/docs`.

- `GET /v3/info` — сколько карточек/рубрик/тестов.
- `GET /v3/rubrics` — список 25 ID и тем **без выдачи полного внутреннего эталона**.
- `POST /v3/prepare` — получить сообщения для своей интеграции LLM (содержит закрытые критерии, только backend).
- `POST /v3/evaluate` — оценить одну тему + red flags.
- `POST /v3/session/start` — начать тему по `card_id`.
- `POST /v3/session/answer` — ответ → оценка → целевое уточнение/завершение.
- `GET /v3/session/{session_id}` — состояние без полной истории.

Пример `POST /v3/evaluate`:

```json
{"card_id":"PY-ASYNC-01","candidate_answer":"time.sleep блокирует event loop. Я заменю ожидание на await asyncio.sleep(2)"}
```

В ответе `criteria` содержит 5 оценок, `score` — максимум 10, `red_flags` — список с цитатами. `human_review_required` всегда `true`, а `needs_review` сообщает об обнаруженных технических проблемах/неуверенности модели.

Пример `POST /v3/session/start`:

```json
{"card_id":"REDIS-CACHE-01"}
```

В ответ придёт `session_id`, который понадобится для `/v3/session/answer`.

**Безопасность:** `/docs` и `/v3/prepare` раскрывают внутренние критерии, нет аутентификации, нет сроков хранения и изоляции данных пользователей. **Запускать только на `127.0.0.1`, с синтетическими кандидатами.** Не публиковать в интернет и не передавать реальные ПДн.

## 5. Как работает адаптивность

1. Первый вызов LLM выделяет атомарные смысловые фрагменты и связывает каждый с одним или несколькими критериями.
2. Python находит каждый фрагмент в исходном ответе, проверяет цитату и назначает серверный ID (`S001`, `S002`, ...).
3. Второй вызов LLM рассматривает все фрагменты, классифицирует их как подтверждающие, частично подтверждающие, противоречащие или нейтральные по каждому критерию и выставляет баллы 0/1/2.
4. Python проверяет полноту ссылок и собирает цитаты из исходного текста. Это гарантирует целостность ссылок, но не гарантирует, что модель выделила абсолютно все важные мысли.
5. Сессия хранит доказательства по текущей теме, не теряя ранее раскрытые критерии.
6. Если подтверждено 8–10 и нет существенных противоречий — `next_topic` (следующую тему выбирает backend/оркестратор, **не делает кадровое решение**).
7. Иначе задаётся уточнение по ещё не проверенному самому слабому критерию (максимум 2 уточнения).
8. Если после двух уточнений недостаточно данных — `insufficient_evidence`. При противоречиях/сомнениях — `needs_review`.
9. После смены карточки/backend должен запустить новую `session/start`. Глобальный сценарий интервью и сохранение в PostgreSQL пока **не реализованы**.

## 6. Почему это не «объективный эталон»

В нынешнем наборе **каждый пример написан под собственную рубрику** — это синтетический учебный набор. Высокое попадание в эти оценки не гарантирует точность на живой речи и сложных ситуациях. Для реальной проверки необходимо:

- двое независимых опытных Python Backend-инженеров для 25 рубрик и 150 оценок;
- реальные варианты перефразирования, опечатки STT и смешанные ответы (правильные тезисы плюс существенная ошибка);
- независимый тестовый набор, не использованный для проектирования рубрик/промптов;
- отдельно измерять ложные завышения, ошибочные red flags, повторение вопросов, задержку и стоимость;
- не оценивать акцент, манеру речи, паузы или формальное образование и не делать автоматическое решение о найме.

Технические ссылки в `rubrics_all_25.json` — **ориентиры для проверки**, а не утверждение, что все 25 карточек прошли документационную или экспертную верификацию.

`knowledge_base.json` — актуальный каталог 25 карточек без критериев и уточнений.

Исходная KB сохранена в `data/legacy/knowledge_base_v1.json` для v1/v2.
Материалы вакансий объясняют **почему проверяется навык**, но не доказывают
правильность технического ответа. Для новой работы используйте только v3.
